## 01 / 先从搬家说起

想象你要把一整间书房搬到另一个城市。把所有书装进一个巨大箱子，途中箱子破了，就得全部重装。如果先拆成八个编号的小箱子，第三箱丢了，只需要补寄第三箱。

> 分片上传的关键，是把一次昂贵的整体操作，变成可以单独确认、单独重试的小步骤。

网络也会“丢箱子”。一个大文件上传到 90% 时断网，如果服务端没有记录已完成的部分，你可能要从头传。分片上传把文件切成带编号的小块，每块独立上传，最后按序拼回去。

## 02 / 到底在解决什么问题

第一是**降低失败后的重试成本**，第二是**允许有限度的并行**。但分片不等于一定更快：如果已经占满上行带宽，增加并发不会突破物理上限，反而增加请求和服务端开销。

```flow
创建上传任务
上传 / 补传分片
有序合并与校验
```

原课提供四个接口：`init` 创建任务、`uploadPart` 上传分片、`detail` 查询已经收到的分片、`complete` 合并文件。断点续传的基础，是客户端能知道“哪些已经成功”。

## 04 / 回到 Java：代码把思想放在哪里

`ShardUploadServiceImpl` 是核心入口。`init` 创建任务记录；`uploadPart` 先查询分片是否已经登记，再写入磁盘和数据库；`detail` 返回已经登记的分片编号。

两张表分别保存文件级任务和分片。分片表对 `(shard_upload_id, part_order)` 建联合唯一索引，用任务与序号识别“同一块”。这是一个与 Java 无关的建模思路。

```text
// 原实现流程的简化表达；并非可直接运行的完整代码
uploadPart(taskId, partOrder, file):
    if 数据库已有该分片记录:
        return
    将分片保存到磁盘
    将分片记录写入数据库

complete(taskId):
    检查分片记录数是否等于预期数量
    按 partOrder 升序读取分片并合并
    如传入 MD5，校验合并文件的 MD5
    更新任务的最终文件路径
```

先查再写并不是原子的。两个并发请求都可能查到“不存在”，然后同时写同一路径。唯一索引能限制数据库重复记录，却不能自动解决文件写入竞争。理解这个区别，比记住一段代码更有价值。

## 05 / 原实现之外，继续追问

### 收到全部分片，等于上传成功吗？

原实现的 `detail` 用“记录数等于预期分片数”设置 `success`。它说明分片已登记齐全，不能证明合并完成、内容校验通过。更明确的任务状态可以是：上传中 → 合并中 → 已完成 / 失败。

### 合并到一半失败了怎么办？

原实现以追加模式打开目标文件，并在复制每块后删除源分片。如果中途异常，或者最后校验失败，重试可能面对残留目标文件和已删除分片。可改为写入临时目标、完整校验后再发布最终文件，并延后清理。这是后续实验题，不是原代码已有的保证。

### 一个指纹，就能代表一个文件吗？

原实现支持 MD5 校验，但任务创建时只是保存 MD5，并未实现“按 MD5 找回旧任务”。文件摘要也不能替代用户身份与授权；如果增加秒传、任务复用，要一起讨论文件访问权限与信息泄露边界。

### 服务有多台机器呢？

原实现将分片放在服务器的本地临时目录。如果请求落到不同机器，另一台机器未必读得到分片。共享存储或对象存储的分段上传、任务归属、超时清理、分片编号校验与配额，都需要额外设计。

## 06 / 用自己的话讲出来

> 我会先确认文件大小、网络条件和恢复要求。用任务 ID 加分片序号标识每块，通过已确认分片列表补传；合并时保证顺序和完整性，再处理并发提交、失败恢复与存储部署。
